Module 1: Concept of Spec-Driven Development

Spec-Driven Development (SDD) is an architectural paradigm that redefines the software
development lifecycle by elevating the specification—rather than the code—to be the
authoritative, executable source of truth for a system. In the age of AI coding assistants, SDD
serves as a deterministic control plane that constrains the stochastic nature of Generative AI,
ensuring that the software generated aligns precisely with architectural intent rather than
probabilistic guesswork.

The following are important considerations, rules and concepts that define the SDD architectural
paradigm.

1. The Core Problem: Vibe Coding

SDD addresses the fragility of "vibe coding", a reactive workflow where developers iteratively
prompt AI agents with vague instructions (e.g., "make it look better") without a structured plan.
This approach relies on the AI "guessing" architectural details, leading to context drift—where
a fix in one area silently breaks established patterns elsewhere—and regression, as the AI
lacks a persistent memory of the project's constraints.

2. The General Theoretical Framework

The SDD framework operates as a closed-loop control system, inverting the traditional
relationship between design and implementation. Instead of documentation being an
afterthought, the specification drives the implementation through a structured, often automated,
pipeline.

A. The Project Constitution (The "Rule of Law")

At the foundation of the SDD workflow lies the Project Constitution (sometimes called
a "memory bank"), a set of immutable, high-level principles that govern every interaction
and generation task. Unlike ephemeral prompts, the Constitution acts as a global rule
engine—enforcing non-negotiable constraints such as "zero external dependencies" or
"always use specific security protocols"—ensuring that the AI never violates the project's
core architectural mandate.

B. The Spec-Driven Workflow (Intent to Execution)

SDD typically follows a structured, multi-phase lifecycle that separates intent (what)
from implementation (how):

1.  Specify: The developer defines the high-level goals, user stories, and functional
requirements in natural language, creating a "living contract" for the feature.

2.  Plan: The AI analyzes the spec against the Constitution to generate a detailed
technical plan, outlining architecture, data models, and dependencies before
writing a single line of code.

3.  Tasks: The plan is decomposed into atomic, implementable units of work,

preventing the AI from getting "lost" in large contexts.

4.  Implement: The AI executes the tasks to generate the code, which is treated as

a derivative artifact that can be regenerated if the spec changes.

C. Human-in-the-Loop Protocols (Governance)

In SDD, the human role shifts from "coder" to "architect" and "governor". The protocol
demands that humans review and validate the Specification and Plan—the upstream
artifacts—rather than just debugging the downstream code. This ensures that human
judgment is applied to intent, policy, and ethics, while the machine handles the
mechanical labor of execution.

D. Testing Gates and Drift Detection

SDD transforms validation from a periodic activity into a continuous, systemic
enforcement mechanism known as Drift Detection. Automated testing gates (contract
tests, schema validation) continuously compare the running system against the
specification; if the implementation diverges from the agreed-upon spec (drift), the
system flags the violation, forcing a correction in either the spec or the code to restore
alignment.

3. Model Differentiation

Different maturity levels of SDD exist depending on how strictly the specification controls the
code:

●  Spec-First: The spec is written initially to guide the AI's first draft but may be discarded

or drift once coding begins.

●  Spec-Anchored: The spec is a living document maintained alongside the code, with
automated tests ensuring the two remain synchronized throughout the lifecycle.
●  Spec-as-Source: The spec is the only editable artifact; the code is treated as a
compilation target that is fully generated by the AI and never manually modified.
