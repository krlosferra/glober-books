## 4. Rulings on the PM's requested decisions

- **DEC-025: CONFIRM WITH CHANGES.** Reasoning: the BRD names `INVALID_STATUS`, `INVALID_RATING` and `RATING_NOT_ALLOWED`; the constitution lets a spec code with the same meaning take precedence; keeping 400 avoids a code outside the constitution's list. The alternative (always `VALIDATION_ERROR` for status and rating) would drop BRD codes. The price is that the status field can appear under two codes; that is acceptable only if tested. Conditions: P-9 (tests), one sentence in BR-001 and BR-002, and the page mapping in P-6. `RATING_NOT_ALLOWED` stays 400 as the BRD states ("400: Invalid rating (not 1-5) or book not completed").
- **DEC-026: CONFIRM.** A tool name is HOW (Module 5 section 2, Specify). Condition: F-15 (name the data state).
- **DEC-027: CONFIRM WITH CHANGES.** The decision to make wire behavior exact is right and needed (Module 4: no expected value, no oracle). Not yet exact: F-01, F-02, F-08. Do not log it as final until Appendix D is consistent.
- **DEC-028: CONFIRM WITH CHANGES.** Fail-closed on an unusable database is right and matches the constitution's fail-closed startup posture; the predicate must be observable (F-07).
- **"UTF-8": contract.** The constitution fixes `charset=UTF-8` on the wire and the response-size bound depends on responses being written as UTF-8 text (5.0); an HTTP client can observe both. Keep, but keep it in the encoding sentences only.
- **"Unicode 15.0": contract (a normative version), not HOW.** Determinism needs a fixed version and a tester needs to pick unassigned code points. Conditions: say "Unicode 15.0" and nothing about the JDK in the spec (the JDK is why 15.0 was chosen, which is Plan material; put that reasoning in the plan); add "changing the version is a spec change". Plan note for later (do not put in the spec): Java's whitespace helper differs from the Unicode White_Space property that BR-006 requires (it excludes no-break space and includes U+001C to U+001F), so the Plan must not rely on it.
- **"100 characters" for a number literal: contract.** It produces a distinct status and code, so it must be observable and exact. Conditions: say it counts the characters of the literal as written (sign, digits, fraction, exponent) and add boundary rows for exactly 100 and 101 (P-9). The unit "characters" is safe because a JSON number is ASCII.
- **Two-fault request not determined by BR-012:** none among the cases I could construct that mix steps; the holes are in the grammar inside single steps (F-08) and in step 2 versus 3 (F-02).
