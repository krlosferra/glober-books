## Binding constraints
1. Order of checks per BR-012: the gate has already judged host, origin, content type, size, route, accept, id shape, query and empty body; then the body shape and field values (strict reader, then `StatusRequest` validation), THEN existence (`BOOK_NOT_FOUND`), then state rules. Field values are judged before existence: `PUT status` on an unknown well-formed id with `{"status":"Done"}` gives `INVALID_STATUS`, not `BOOK_NOT_FOUND` (T-38). Status `"Completed"`, `""`, `null`, `{}` give `INVALID_STATUS`; `5` or `true` give `MALFORMED_REQUEST` (T-19), reusing Task 20/21/30 semantics.
2. Status change: through `Book.changeStatus(target, clock)` with the injected clock; entering completed sets `date_completed`; leaving completed clears rating and `date_completed` in the same transaction as the status (BR-004, BR-008, DEC-023); a same-state change changes nothing (S-04, S-11). One `@Transactional` unit per request, no query in a loop.
3. Delete returns the removed book (5.7) and a second delete is `BOOK_NOT_FOUND` (S-06); get returns the book as in 5.3; ids are the lower-case UUID string already validated by the gate (do not re-implement the id rule; the service takes the string and looks it up with a bound parameter).

E-18 on real endpoints: `DELETE` with `Content-Type` and no body passes the gate; a one-space body gives `400 MALFORMED_REQUEST`. Complete the real-port rows left to this task by Task 16 (E-24 row 1, E-27 rows 1 and 2, T-14) and say which you completed.
