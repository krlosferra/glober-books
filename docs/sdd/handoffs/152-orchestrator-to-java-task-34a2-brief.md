## Scope

Tests: `JarDataLocationIntegrationTest` (the packaged jar on an empty temporary location), `StartupRefusalIntegrationTest`; reuse `support/AppProcess` (edit only if needed). Out of scope: stored-library validation, hot journal and second-instance proofs beyond criterion 5 (Task 34b), any new dependency, any change to `pom.xml` or to `backend/config/**` (the resource folder: ASK FIRST). If the wiring cannot be done without a forbidden change, STOP and report.

## Binding constraints
1. Wiring (criterion 1): the data source is built only as `DataDirectoryGuard.check(...)` then `SqliteDataSourceProvider.create(Guarded)`, after `StartupPolicy` and before the first connection; Hibernate and Spring Data use that data source. Remove the unguarded `create(Path)` and `create(String)` overloads or make them unreachable from configuration (package-private, used only by existing tests that need a plain database; adapt those tests instead of widening the API) and add a test that fails if any data source bean is built another way (SEC-F-185 item 5). Keep the data location property compatible with README, `AppProcess` and the E2E launcher (`--spring.datasource.url` or whatever they pass today); if it must change, update those callers in the same change and say so.
2. Paths: normalize with `toAbsolutePath().normalize()`, never `toRealPath()` (a path through a link is refused on purpose); `InvalidPathException` (NUL byte etc.) and any malformed location become a fixed refusal, never a stack trace; the default relative `data/` must work on the jar when started from `backend/` as the README says (prove it).
3. Pragmas read back from the RUNNING jar (not only in the provider test): `foreign_keys` on, `trusted_schema` OFF, `busy_timeout` 5000, extension loading refused, pool size 1, journal mode as designed. Read them through a test-only path that does not exist in `src/main` (A-09): e.g. open the same database file from the test JVM after stopping the app is NOT valid for connection pragmas, so use what the plan allows (a startup log line is not acceptable if it leaks); if there is no legitimate way without a test-only switch, STOP and report the limit instead of adding one. A first option: a Spring Boot test in-process (`@SpringBootTest` with the real configuration class) reading the pragmas through the application's own `DataSource`, plus the jar-level behaviour proofs (second instance refused, modes, refusals) for the rest.
4. Jar-level proofs (criteria 2, 3, 5), reusing `AppProcess` on a random free port (never 8080 or 18080): empty location under umask 022 and 000 (run the child through `sh -c "umask N && exec java ..."`): directory 0700, `tmp` 0700 and `library.db` 0600 BEFORE the first connection, and after an add every journal or companion file no wider than 0600 (this closes SEC-F-181: make sure a `-journal` file is actually observed, for example by holding a transaction or inspecting during a write, or state honestly that SQLite removed it and what you did instead); a pre-existing 0755 directory or 0644 file is refused with non-zero exit and nothing created or changed; a symlinked `data` or `library.db` is refused; another owner via `chown` as root where possible (state the limit otherwise); an uncreatable directory (e.g. a file where the directory should be, a 300-byte name) fails cleanly with a fixed reason and nothing is created outside the guarded directory; a second instance on the same file exits non-zero with a fixed reason while the first keeps serving with its data unchanged (US-009.7, C-12). For each refusal compare the tree snapshot (hashes, modes, owners, link targets) before and after (`support/TreeSnapshot`).
5. Reporting (criterion 4): every start refusal goes through `StartupFailureAnalyzer` with a fixed string; assert that the console and the log of every refusal run hold no path of a book, no cell value, no data location path and no stack trace beyond what the policy allows (check what `StartupPolicy` already does and be consistent). Security follow-ups to carry: SEC-F-182 (a database file with link count above 1: refuse it in the guard if the change is small, add a test; otherwise record why not), SEC-F-184 a and b (partial creation left behind after `CANNOT_CREATE`: clean up only what the guard itself created, inside the guarded directory; compare the owner by numeric uid when the platform allows, otherwise keep the name check and say so). Liaison follow-ups: reword the guard Javadoc that says a refusal "creates nothing" (L-1); name `tmp` in the delivery; add new test classes (the guard test is at the line limit).
6. README: if the run instructions or the E2E launcher need a change (data location, "pass the real path, a path through a link is refused on purpose"), make the minimum edit in the same change and list it. Do not claim anything the tests do not prove.
7. All files at or under 300 lines; no `Thread.sleep` for readiness (poll with a deadline); stop and clean up every process; no test-only route, property or switch in `src/main` (A-09; the existing source scan must stay green); no logging of paths of books or values. Expected values come from the spec and the security notes.
