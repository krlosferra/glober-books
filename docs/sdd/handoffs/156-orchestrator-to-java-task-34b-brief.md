## Binding constraints
1. Order (criterion 1, Security's order): the validator is read-only and runs before anything writes. First the file header (bytes 18 and 19: a WAL-marked file is refused), the header size test being skipped when a non-empty `-journal` exists (a hot journal must be allowed to roll back first); then `sqlite_master` (exactly one table `books`, no other object except the key index, no view, trigger or virtual table, and the stored DDL equals the plan's DDL or each named CHECK is present); then `quick_check`; then the rows with `LIMIT 5001`, a SQL `length()` and `typeof()` pre-check BEFORE any text is fetched (so one oversized cell is never loaded), and the title and author lengths in code points in Java (SEC-F-068). Rows are judged for format, limits and INV-1 to INV-4 (rating only when completed; `date_completed` iff completed; date and id formats), a NUL inside a title, and more than 5,000 rows.
2. Refusals (criterion 2): each of the listed cases (non-database; WAL-marked; damaged; other structure; no tables; view, trigger or virtual table; `books` without its CHECKs; an extra index; a row violating a format, limit or INV-1 to INV-4; a NUL in a title; one oversized cell; more than 5,000 rows) makes the start fail non-zero, serves no request, reports a fixed reason (one fixed string per category; they may share the analyzer from 34a-2 but must not be a single catch-all; Liaison F-4 of 34a-2), and leaves the bytes unchanged by SHA-256 of the main file (and of any journal). A reason never contains a cell value, a path or SQL text; the console shows no book data.
3. SEC-F-181/Liaison F-1 (34a-2): in the refusal runs of invalid-row cases, plant a recognizable marker in the invalid row (title) and assert the marker never appears on the console or in the log (so the "no book data" claim is not vacuous).
4. Hot journal (criterion 3, R-20): (i) a valid file plus the genuine journal of a kill during an add that grew the file is recovered and accepted (produce a real hot journal: kill -9 a writer mid-transaction, or construct one with SQLite's own journal by an uncommitted transaction whose process is killed; say how you produced it); (ii) an invalid main file plus a genuine hot journal: non-zero exit, a fixed reason with no book data, and the SHA-256 of the file after the rollback equals its SHA-256 after the refusal (no write after the refusal; CR-9 judges the file after the rollback: compute the post-rollback hash with a separate read-only reference rollback on a copy); (iii) a planted garbage journal beside a valid and beside an invalid file is ignored and the bytes are unchanged. If a hot journal cannot be produced in this sandbox, STOP and report; do not fake it.
5. Absent or empty file (criterion 4): created by the guard (mode 0600) and the schema created; a valid database opens and no book is altered (compare a hash of all rows before and after).
6. Second instance (criterion 5): 34a-2 already proves a second instance exits 1 while the first keeps serving. Here add `SecondInstanceIntegrationTest` for the same reporting through the validator path (the second instance runs the validator against a database held by the first: it must not report a false "damaged"; it exits non-zero with the fixed "in use" reason, the first keeps serving with its data unchanged by comparing full list bodies and a hash of rows via the API). Do not duplicate 34a-2's tests; extend where the validator changes behaviour.
7. SEC-F-186 (optional, small): call `NativeDirectoryModes.narrow` in a `finally` so a refused start does not leave 0644 extracted files in `tmp`, and remove stale extracted files found in `tmp` at start; if you do, add a test; if not, record why not. All files at or under 300 lines. No test-only switch in `src/main` (A-09; the source scan must stay green). No logging of cell values or paths. Expected values come from the spec and the security notes.
