## Judgements
**A. Tomcat-first pages (SEC-F-151, 128, 172): CLOSED, accepted.** Own probes on the jar: `/%2e%2e/`, `/..;/`, `%2f`, `%00` give 400 HTML (435 bytes); `/WEB-INF/web.xml` and `/META-INF/x` 404 (431); TRACE 405 with `Allow` (449); a 9,000-byte line 400; a `<script>` query with a bad escape 400. Headers are only Content-Type, Content-Language, Content-Length, Date, Connection: no `Server`, no product, version or echo, next request served. The test pins (`PreApplicationIntegrationTest`, `RawRules.assertNoDisclosure`: tomcat, apache, coyote, spring, java, jetty, x-powered-by, version pattern, `Server` header, echo of the planted text) are sufficient. Accepted by Security under constitution 1.5 (1 of 5 this phase), covered by R-13 and R-23.

**B. SEC-F-147 / R-24: can stay accepted only if the Sponsor renews it (MEDIUM).** Real exposure: a local process (any user, loopback is unauthenticated) needs 8 sockets to slow every request by seconds (body drip with reconnect) and about 130 sockets (idle, one byte per 2 s) to stop the service for as long as it holds them; I held it for 100 s with no server cut. The attacker is already able to read and delete all data through the unauthenticated API, and a web page cannot send a slow HTTP/1.1 request, so no new confidentiality or integrity impact. Delivery 164's "12 held connections did not stop a GET" is true but understates it: the limit is 128, not 8. Mitigations in Tomcat 11.0.27: none for line or header time; `connectionUploadTimeout` and `maxSwallowSize` touch only the body. A real fix would be a different connector or a proxy: disproportionate for a local tool. Recommendation: renew R-24 for the release, release notes sentence.

**D. E-37 row 1 (`GET  /  HTTP/1.1`), assessment for the Sponsor.**
- RFC 9112 section 3 (quoted from memory; I cannot fetch the RFC here, so check the wording): the request line is defined with single SP separators, but "recipients MAY instead parse on whitespace-delimited word boundaries" and treat SP, HTAB, VT, FF or bare CR as the separator; it warns that "lenient parsing can result in request smuggling security vulnerabilities if there are multiple recipients of the message and each has its own unique interpretation of robustness" (section 11.2). Section 2.2 also says a server SHOULD ignore at least one empty line before the request line, and section 3 lets a recipient accept a bare LF as a line end.
- Tomcat 11.0.27 (bytecode of `Http11InputBuffer.parseRequestLine`: bytes 32 and 9 in the method, target and version phases) accepts runs of SP and HTAB only. Own probes: two spaces after the method, before the version, both, tab after the method, tab before the version, `GET /api/v1/books\t HTTP/1.1`, leading CRLF, bare LF endings: served. Leading space, VT, FF, bare CR separator, trailing space, a third token, a space or tab inside the target, lower-case version: 400 HTML. A request with no version (HTTP/0.9 form) has no Host, so the gate answers INVALID_HOST.
- Does anything make the gate and the container disagree? No. `RequestGateFilter` reads `getMethod()`, `getRequestURI()`, `getHeaders()` from the container's already parsed request; whitespace never reaches it. Probes: `POST\t...`, `DELETE  /api/v1/books/abc  `, `GET /api/v1/books?status=bogus\t`, an absolute-form target with a foreign host (container 400), and requests refused by the gate with a second request smuggled in the body (bad content type, bad Host, foreign Origin, unknown route, PUT on the list, chunked): one response each, no desync. TE variants (`Transfer-Encoding :`, tab, `xchunked`, `chunked, identity`, CL plus TE) are 400 or 501.
- Can it be enforced? Tomcat 11.0.27 has no connector property for a strict request line (checked the `Connector` and `AbstractHttp11Protocol` classes: only `encodedSolidusHandling`, `rejectSuspiciousURIs` and size and time settings). A servlet filter or valve gets the parsed request, not the raw bytes (`unparsedURI` has no whitespace), so neither can see it. The only route is a custom `ProtocolHandler` or input buffer, i.e. replacing the HTTP parser: high risk and cost, for no gain here. I cannot determine from the jar whether a future Tomcat adds a switch.
- Severity: INFO (CWE-444 class "Inconsistent Interpretation of HTTP Requests", not reachable with one parser and loopback). Standards: RFC 9112 sections 3 and 11.2; OWASP ASVS 5 section on HTTP message structure validation (V4.2, framing: the CL/TE and header-name rules are met, there is no single-SP rule; verify the item numbers in your copy); CWE-444.
- Recommendation: accept as a documented limit and amend the spec, do not fix before the tag. R-26 (Pending Sponsor) is written for this. It does meet the desirable standard where it matters (framing conflicts, duplicate Host and Content-Length, whitespace before the colon, obs-fold, bare CR all refused); it is the spec row, not the standard, that is stricter than the RFC.

**E. E-28 `FOO` without `Content-Type` gives 415.** No security impact: the content-type check runs before the route and gives the same generic envelope for every route and method, so nothing is enumerated; 415-before-405 does not matter. The Appendix D prelude says requests carry `Content-Type: application/json`, so the row as written is met (`FOO` and `get` give 405). PM may add a sentence.

**F. T-33 log hygiene: CONFIRMED with one nuance.** About 200 requests with CR, LF, U+2028, U+2029, U+0085, ESC (and NUL) in id, query value and name, path, JSON title and author (escaped and raw), Origin, Content-Type, Accept, Referer, User-Agent, Sec-Fetch-Site, X-Forwarded-For, Host, method, version: the application log did not grow (45 lines before and after) and no raw control character is in the file. The one exception is Tomcat's own INFO line for the first malformed header, target or method of a process (SEC-F-195): it echoes up to 8 KiB of attacker text on one line (stack trace included, joined by `_`), control characters shown as `0x1b`, nothing raw (10 fresh-process probes: ESC, NEL, U+2028, CR, LF, 0x9b, NUL in name, space in name, ESC in target and method). Titles never appear. SC-37 holds.

**G. Ledger close-outs.** SEC-F-166 CLOSED: cold first duplicate at 2,500 books 0.62 s, then 0.04 s; the delivery's 5,000-book figures (392 ms add, 428 to 488 ms duplicate) are well under 2 s. Slow readers (S-6): not reproduced as "never cut". No response-write timeout is needed (the container already applies one); accept with R-24 and mention in the release notes.
