## 4. Rulings on the PM's questions

| # | Question | Ruling |
|---|---|---|
| 1 | U+200C rejected (Persian) | The usability cost is real: Persian, Urdu, Kurdish and several Indic scripts need ZWNJ for correct spelling, and ZWNJ is as invisible as ZWJ, which BR-006 already allows. Rejecting is safe but not necessary. **Recommended (my preference): allow U+200C and U+200D under one positional rule**: a joiner must not be the first or last code point of the trimmed text, must not be adjacent to another joiner, and must not be adjacent to a code point of category Zs. This keeps emoji ZWJ sequences and Persian spelling and removes the "invisible first or last character" hole that exists today for U+200D. **Acceptable alternative**: keep rejecting U+200C with the limitation written into the spec (Out of Scope: "titles that need a zero-width non-joiner, for example Persian, cannot be stored") and a DEC entry for the Sponsor. Security does not require either; it requires that U+200D gets a positional rule in both cases. |
| 2 | Tag characters rejected (flag-subdivision emoji) | **Keep rejected; accept the cost.** Tag characters U+E0000 to U+E007F are the standard hidden-ASCII channel against LLM agents and render invisibly. The only legitimate use is the three subdivision flags (England, Scotland, Wales). Write the limitation in the spec (one line in Out of Scope). |
| 3 | Combining marks uncapped within the length limit | **Not acceptable as written (SEC-F-044).** Required: (i) at most 8 consecutive code points of category Mn, Mc or Me (PM may raise to 16 with a stated reason; never above 30, the Stream-Safe Text Format limit of UAX #15); (ii) at most one variation selector (U+FE00 to U+FE0F, U+E0100 to U+E01EF) in a row; (iii) a text must not begin with a combining mark or variation selector. Real scripts stay within these (Arabic with full vocalization, Hebrew with cantillation, Vietnamese decomposed, Tibetan stacks, Japanese ideographic variation sequences). Cost: Zalgo-style and data-carrying decoration is rejected with the existing "contains characters that are not allowed" message. |
| 4 | Unpaired surrogate and invalid UTF-8 as `MALFORMED_REQUEST` | **Agree.** These are encoding faults of the body, not values of a field; no field can be named, and a decoder that fails cannot tell where a field starts. Required: the decoder must be strict (report, never replace with U+FFFD) and the escape check must cover pairs in the wrong order; cases T-26 to T-28 pin this. A literal valid U+FFFD stays a normal character. |
| 5 | 16 MB worst-case list response | **Acceptable for a single local user**, under these conditions: the arithmetic stands (5,000 x 3,100 = 15.5 MB; JSON escaping cannot inflate it because control characters are banned, so no 6-byte `\u00XX` escapes, and a backslash or quote costs 2 bytes against up to 4 bytes of the astral worst case); the contract rule "UTF-8, not escapes" is tested by C-05 on the real port; C-05 gets a recorded time (no gate, as in DEC-020); SEC-F-054 (5,000-entry page) is answered. Failing that the Sponsor should accept R-02-style residual in writing; I do not need that if the conditions hold. `no-store` and no compression are fine. |
| 6 | OPTIONS and HEAD | **Accept 405 for both** (smaller surface, no cacheable semantics, SC-18). Required: the `Allow` header on every 405 listing only defined methods (E-29), and the transport checks run first, so a cross-origin preflight is 403 and a same-origin OPTIONS without content type is 415 (E-04, E-05 as written; accept the oddity that OPTIONS without a JSON content type gets 415). Note the deviation from RFC 9110 (general-purpose servers should support HEAD) in DEC-027. |
| 7 | Sub-order Host, Origin and Sec-Fetch-Site, content type, body size | **Agree.** Cheapest and most specific checks first; size last because it may need the body. Required additions: the filter decides on `Content-Length` before reading, counts bytes of chunked bodies even when no handler will read them (E-32), and does not read a body that an earlier check rejected (E-33); the plan must set `server.tomcat.max-swallow-size` low (suggest 64 KiB) so a rejected 10 MB request does not make the server swallow 2 MB per request. One usability consequence to document: a cross-site top-level navigation to `/` (clicking a link to `http://localhost:8080/` from another site) carries `Sec-Fetch-Site: cross-site` and gets 403 JSON; typing the address or a bookmark (`none`) works. |
| 8 | E-10 and E-20 container-level under R-13 | **Agree**, with the sets tightened: the container may answer only the cases it parses before the filter (HTTP/1.0 or 1.1 without `Host`, duplicate `Host` headers, invalid request line, over-long line or header, CL+TE, bad `Content-Length`); status 400, 414, 431 or 505; no product, no version, no echo; the application keeps serving. A single `Host` header with a comma list is the filter's case: exactly `INVALID_HOST`. |
| 9 | Invalid body for an unknown id reports the body error | **Agree; no information leak of consequence.** (a) Existence of an id is already readable through `GET /books/{id}` and the list; ids are random (122 bits), but the single user can list them all anyway. (b) The order makes the oracle weaker, not stronger: an invalid body gives the same answer for an existing and an unknown id, so only a valid body probes existence, exactly like `GET`. (c) `DUPLICATE_BOOK` returning the existing book discloses nothing a list does not, and cross-site pages cannot make the request (SC-28). The one residual is R-16 (other local users), which already sees everything. |

Other points settled: `GET /books/{id}` and `DELETE .../rating` can stay (no security reason to remove; each has a defined, tested behavior). DEC-025, DEC-026 and DEC-028 are acceptable from a security viewpoint; DEC-027 is acceptable and gains the text of section 5 below.

## 5. Required spec changes (exact text)

1. **BR-006 item 6, replace the last two sentences** and add 6b to 6d:
   "6. It must not contain: control characters (Cc); format characters (Cf) other than U+200C and U+200D; tag characters (U+E0000 to U+E007F); line and paragraph separators (Zl, Zp); private-use code points; noncharacters; or code points unassigned in Unicode 15.0. U+FE0F is category Mn and is allowed. White space of category Zs is allowed inside the text.
   6b. Visible content: the text must contain at least one code point of category L, N, P or S other than U+115F, U+1160, U+3164, U+FFA0 and U+2800, and must not begin with a code point of category Mn, Mc or Me.
   6c. Marks: at most 8 consecutive code points of category Mn, Mc or Me, and at most one variation selector (U+FE00 to U+FE0F, U+E0100 to U+E01EF) in a row.
   6d. Joiners: U+200C and U+200D must not be the first or last code point of the text, must not be adjacent to each other, and must not be adjacent to a code point of category Zs.
   A violation of 6 to 6d gives `VALIDATION_ERROR` with the message "contains characters that are not allowed"." Add the limitation sentence for tag characters (and for ZWNJ if the alternative of ruling 1 is chosen).
2. **5.0, add after "Strict parsing":** "Every failure raised by the JSON parser, its configured limits (nesting depth, string, name and number length) or the UTF-8 decoder is `400 MALFORMED_REQUEST`; none is `INTERNAL_ERROR`, and none takes longer than 300 ms. The decoder reports malformed input and never replaces it. The following are invalid JSON for this API: a byte order mark, comments, trailing commas, single-quoted strings, unquoted names, a raw control character inside a string, `NaN`, `Infinity`. Member names are compared after unescaping." Add T-22 to T-33.
3. **BR-011 and 5.0, replace "after URL decoding" with:** "The id segment is validated as sent: any `%` in it makes it malformed (`400 MALFORMED_REQUEST`). Fixed path segments are matched as sent; an encoded form of a fixed segment is `404 NOT_FOUND`. The route is matched structurally before the id is judged: `POST /api/v1/books/not-a-uuid` is `405`, `GET /api/v1/books/not-a-uuid/other` is `404`." Add E-24 to E-27.
4. **BR-012 step 2 and 5.0, add:** "Malformed percent-encoding in the path or query is `400 MALFORMED_REQUEST`. A query string is a list of `&`-separated `name=value` pairs; the empty query (`?`) means no parameters; an empty pair (`&&`, trailing `&`), a name without `=` that is not `status`, and any `;` handling other than treating `;` as part of the value are not allowed: an empty pair is `MALFORMED_REQUEST`. Names and values are percent-decoded once before comparison. A query string on `/`, `/index.html` or any static path is `400 MALFORMED_REQUEST`." (If the PM prefers to ignore queries on static paths, say so explicitly and add a test; this review prefers rejecting: one rule for the whole application, no reflected-parameter surface.)
5. **5.0 Requests, add the Content-Type grammar:** "The media type `application/json` is compared case-insensitively. The only allowed parameter is `charset` with the unquoted value `utf-8` (case-insensitive); optional white space around `;` is allowed. Any other parameter, a quoted charset, a list, or more than one `Content-Type` header is `415`." Add E-34. Add for `Accept`: "A q-value of 0 excludes a type; an unparseable `Accept` header is `406`." Add E-35.
6. **5.0 Only the paths and methods below exist, add:** "Every other method, `TRACE`, `CONNECT`, unknown and lower-case method names included, is answered by BR-012 and ends as `405` (or by the container, R-13); no response ever echoes the request. Every `405` carries `Allow` with the methods defined for that path (never `HEAD` or `OPTIONS`). Static responses carry no `ETag`, `Last-Modified` or `Accept-Ranges`; `Range`, `If-None-Match` and `If-Modified-Since` are ignored and the full body is returned with `200`. The server sends no `206`, `304`, `416` or `101`." Add E-28 to E-31.
