## 3. Probe results (jar of HEAD; "same" = SHA-256 of the main file before and after)
Header and structure (all exit 1, marker `ZQXDATA` in the rows never on the console, file same unless noted):
- bytes 18, 19 = 2, 2 (WAL_MARKED); only byte 19 = 2 (WAL_MARKED); magic changed; truncated by one page (DAMAGED); truncated to 50 bytes (NOT_A_DATABASE); page size 512 and 768 (DAMAGED). All same.
- planted garbage journal beside a file truncated by two pages: size test skipped, refused by `quick_check`, journal deleted by SQLite, main same. Trailing junk plus garbage journal: accepted and served (SEC-F-192a); without the journal refused.
- extra table, extra index, partial unique index, `sqlite_stat1`, `COLLATE nocase`, no CHECKs, generated column, `WITHOUT ROWID`, UTF-16 database: SCHEMA_DIFFERS or its neighbour reason, same. View, trigger with a `DELETE` body, trigger with a `SELECT`: FORBIDDEN_OBJECT, file same (nothing was executed: the rows were still present, bytes identical). Virtual table is covered by the delivery's FTS5 test, not re-run.
- `application_id` and `user_version` set: accepted (INFO). Header with bytes 24 and 92 different and junk: DAMAGED but the file changed (SEC-F-190).
Rows (CHECKs bypassed with `ignore_check_constraints` to build the fixtures; STRICT bypassed with a non-strict table whose stored DDL was then replaced through `writable_schema` by the exact schema text):
- NUL after the first character: INVALID_ROW (the CHECK sees length 2). Leading NUL: DAMAGED. Blob in title and in id: DAMAGED. Rating 2^32 + 1, 3.5: DAMAGED. Rating on an unread book, completed without date, date on an unread book, upper-case id, empty title, 501 code points: DAMAGED. `2026-13-45T25:61:61.000Z` and `2026-02-30T...`: INVALID_ROW. 500 code points of 4 bytes (2,000 bytes): accepted. Invalid UTF-8: accepted, lossy.
- 5,000 maximal rows (title 500, author 200, 4-byte code points; 14.8 MB list body): started in 5.3 s; 5,001 rows: TOO_MANY_BOOKS in 2.1 s. 500 MB freelist file: started in 5.1 s. 4 GB sparse file with a lying page count: DAMAGED in 2.4 s. Oversized cells: SEC-F-191.
Hot journal (genuine: python writer, `cache_size=5`, `synchronous=FULL`, 3,000 rows of 400 bytes, SIGKILL while uncommitted; reference rollback = plain connection on a copy):
- valid + journal: accepted, 30 books, hash after run = reference. Invalid (extra table) + journal: SCHEMA_DIFFERS, hash after refusal = reference, marker not on console. Transaction that drops the extra table (main looks valid, rollback makes it invalid): refused, hash = reference. Transaction that adds a table and a view (main looks invalid, rollback makes it valid): accepted, hash = reference. Verdict: judged after the rollback, safe, no write after the refusal.
- genuine journal of another database (same page size) beside a valid library: rolled back onto it, result judged and served (SQLite journals carry no database identity): R-20 as accepted.
- garbage journal (random 700 bytes, magic-like prefix) beside valid: accepted, main same, SQLite deletes the journal. All-zero journal: left in place, main same. Journal beside a text file: NOT_A_DATABASE, both files same. Real hot journals are rolled back, not deleted: SQLite deletes a journal without rollback only when its header does not validate, and the journal header is synced before any page of the main file is written (`synchronous=FULL`), so there is no valid journal to lose. Acceptable.
- journal + WAL chain: SEC-F-189.
Second instance and locks: second instance on a 25-book library held by a serving first one: exit 1 in 2.1 s, fixed "could not be opened or is in use" text, none of the validator texts, first still serving the byte-identical list, file same. Another process holding an exclusive `fcntl` lock: exit 1 in 2.1 s, same text; holding a shared lock: exit 1 in 8.1 s (claim busy), same text. The header lock is shared and released before the pool opens; it cannot defeat the exclusive claim (the claim is SQLite's own and is taken afterwards) and denies service only to a process that could equally hold SQLite's lock. A file system without lock support: `tryLock` raising an IOException is mapped to the "in use" reason (fail closed by reading the code; not testable here).
Console: across all refused runs, 0 lines with `library.db`, a stack frame, `Caused by`, SQL or the marker; the only path on the console is the existing start line (cwd, SEC-F-187c). The nine reasons are fixed enum texts with no cause kept (`Refusal` has no cause, the `SQLException` is discarded, the analyzer prints `text + "."`).
