## Key judgments
(a) Rating literal codes against the spec. Every row in the delivery table matches the spec: T-17 (INVALID_RATING), T-18 (MALFORMED_REQUEST), T-31 (the three numbers INVALID_RATING within 300 ms; the nested bodies are the parser limit, not this task), T-32, T-37 (100 digits INVALID_RATING, 101 digits MALFORMED_REQUEST), US-003.2 (`-1`, `-0` invalid). The `1e999999999` case runs in under 1 ms warm and the token is judged from its text with no BigDecimal. The delivery's finding 1 is right: spec line 393 says a number is measured "in characters as written (sign, digits, fraction, exponent)", up to 100 judged by value, above 100 `MALFORMED_REQUEST`. So a minus sign plus 100 digits (101 characters) must be `MALFORMED_REQUEST`, and Jackson's `MAX_NUMBER` counts digits only. This is not a Jackson 3 behaviour that differs from the plan in a way that changes the spec outcome; it is a plan-versus-spec gap (the plan assumed the Jackson constraint equals the spec rule). The implementer reported it instead of changing `JacksonConfig`, and fixed it locally. I ACCEPT the choice of putting the check in `RatingValue.Reader` rather than `JacksonConfig`: changing `StreamReadConstraints` is Security's call and cannot count characters anyway (the constraint is digit-based), and rating is the only numeric input field today. It departs from "STOP on a Jackson difference" in process only; the outcome is spec-correct, covered by tests (minus plus 100 nines is INVALID, minus plus 101 nines and over-100-character decimals are MALFORMED), and flagged. Conditions: (1) Security confirms (the implementer asked); (2) PM records a plan amendment ("number length is judged by the deserializer on the text as written; `MAX_NUMBER` is a backstop on digits") and a one-line comment note in `JacksonConfig` can wait for a task that touches it; (3) any future numeric field must reuse the same text-length rule (add to the Task 31 brief and the Phase 5 checklist).
Weak oracle check: the over-100-character decimal rows (`0.00...01`) have no explicit spec row; they follow from line 393 and are consistent with it. Fine.

(b) Domain exception. `IllegalStateException` is accepted for now (the domain must not import `error`; the plan names nothing; this is a plan gap). It is a risk, not a defect: `IllegalStateException` is also thrown by startup code (`SqliteDataSourceProvider`, `StartupPolicy`, `StaticAssetCatalog`), and `GlobalExceptionHandler` has a catch-all `Exception` handler giving `INTERNAL_ERROR`. A service that catches `IllegalStateException` broadly could mislabel a real fault as `RATING_NOT_ALLOWED`. Recommendation for Task 31: BR-012 step 8 says the state rule `RATING_NOT_ALLOWED` is judged in the service from the loaded book's status inside the transaction (`status != COMPLETED` pre-check, which keeps the order of checks, T-36), then calls `assignRating`. Do not catch `IllegalStateException`; let it be the defence (it would surface as `500`, which is correct for a broken invariant since the pre-check and the call run in the same transaction). If the PM prefers catching, require a dedicated type, for example a `domain` exception `RatingNotAllowedException extends IllegalStateException` (added in the Task 31 brief as a 4th production file or in a small follow-up commit), and the plan gets an amendment. My recommendation: pre-check, no catch, no new type; this needs only a sentence in the Task 31 brief.

(c) `INVALID_RATING` handling is NOT covered by Task 31's text. `tasks.md` Task 31 production list is `BookService`, `BookController`, `RouteTable`; no `error` package file. `GlobalExceptionHandler.handleInvalidBody` turns a binding failure into `INVALID_STATUS` only for field `status`, otherwise `VALIDATION_ERROR`. `RatingRequest` carries the marker and has no constraint annotation, so it never fails binding. `ApiException` carries only a code (no `details`), while spec 5.6 and Appendix A need `details: [{field: "rating", message: "must be an integer from 1 to 5"}]`. Some file in `error` must change (either `BookValidationException`/`ErrorBodyFactory` usage with a rating problem, or a new handler). The message "must be an integer from 1 to 5" is already in the fixed list (line 579). Also T-36 and T-38 (field values before existence) force the controller or service to check the marker before the lookup. Required PM action: amend Task 31 (production list and acceptance criterion: "a rating marker or a missing member gives `400 INVALID_RATING` with the one `details` entry, before the existence check, and also for an unread book (T-36)"), or move that mapping into a small step. This is a follow-up, not a Task 30 defect: the Task 30 scope excluded the endpoints and the advice.
